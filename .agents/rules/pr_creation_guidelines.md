# PR Creation Guidelines

This document defines mandatory engineering guidelines for creating Pull Requests, branch naming conventions, commit message formatting, pre-commit checks, and post-creation workflow buffers.

---

## Mandatory PR Creation Rules

### 1. Mandatory Branch Naming Conventions
- **Required Branch Syntax**: All git branches created for features, bug fixes, refactoring, or maintenance MUST follow the strict `<category>/<kebab-case-description>` naming convention.
- **Valid Categories**:
  - `feat/`: New feature additions or capabilities (e.g., `feat/enforce-pr-comment-integrity`).
  - `fix/`: Bug fixes or defect resolutions (e.g., `fix/jobset-reconciliation-timeout`).
  - `refactor/`: Code structure improvements without functional changes (e.g., `refactor/pep8-compliance`).
  - `chore/`: Maintenance, dependency updates, or build configuration (e.g., `chore/bump-kueue-version`).
  - `docs/`: Documentation additions or updates (e.g., `docs/ctk-installation-guide`).
- **Forbidden Branch Naming Anti-Patterns**:
  - NEVER use un-prefixed branch names (e.g., `enforce_pr_comment_integrity`).
  - NEVER rely on raw worktree directory names or task IDs without verifying `<category>/<kebab-case-description>` format.
  - NEVER use underscores (`_`) in branch names; always use hyphens (`-`) for word separators.

### 2. Pre-Commit Linter & Test Verification
- **Run Pre-Commit Hooks**: Before committing changes, ensure all repository linter hooks pass (Bazel buildifier, Go formatter, addlicense, Ruff Python linter).
- **Run Unit Tests**: All unit tests associated with modified components must pass cleanly before creating a commit (`bazel test //...` or script unit tests).

### 3. Commit Message & PR Description Formatting
- **Title**: High-level, concise summary prefixed with category type (e.g., `feat: enforce PR comment integrity rules to prevent skipped review comments`).
- **Motivation & Rationale**: Clearly explain *why* the change was made, including background context or failure modes prevented.
- **Key Changes Summary**: Bulleted list highlighting major modifications across code, rules, or skills.
- **Mandatory Description Tags**: All CL/PR descriptions MUST end with mandatory system tags placed at the very bottom after all human-readable text:
  ```markdown
  TAG=agy
  CONV=<conversation_id>
  ```

### 4. PR Creation Procedure via GitHub CLI
- **Command**: Use `gh pr create` with explicit `--title` and `--body` flags.
- **Verification**: Verify that the PR link generated by `gh pr create` is valid and accessible.

### 5. Post-PR Creation CI Wait Buffer
- **Wait Buffer**: When creating or updating a non-draft PR, wait approximately **2 minutes** after PR creation to allow GitHub CI status checks and automated PR review bot passes to execute.
- **Proactive Feedback Check**: After the wait buffer, inspect incoming inline review comments or CI check results.
