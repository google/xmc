# Storage Layer Guidelines (`internal/storage`)

Follow these rules when adding or modifying code under `internal/storage/`:

## 1. No Business Logic in Storage
- Storage packages are strictly responsible for data persistence (queries, mutations, row scanning, proto marshaling) and transaction execution.
- Do **not** place business logic, state transition rules, status diffing, child state count calculations, or multi-step domain orchestration in `internal/storage` or its backend subpackages.
- Business orchestration belongs in the service layer (for example, `cmd/experiment_state_server/` or `internal/`).

## 2. Manage Transaction Boundaries in the Caller (`TransactionRunner`)
- Multi-step or cross-entity read-modify-write workflows must be orchestrated outside the storage package using `storage.TransactionRunner.RunInTransaction`:
  ```go
  err := txRunner.RunInTransaction(ctx, func(ctx context.Context, tx *storage.Transaction) error {
      // Orchestrate reads and writes via tx.WorkUnits, tx.Experiments, etc.
  })
  ```
- Expose composable, single-responsibility read and write primitives on the transaction-scoped repositories (`WorkUnitTxRepository`, `ExperimentTxRepository`, `StatusMessageTxRepository`, `StatusHistoryTxRepository`, `PauseStateTxRepository`, `PausedTaskTxRepository`) instead of creating monolithic transaction methods inside storage backends (see [`README.md`](README.md)).
- Inside `RunInTransaction` callbacks, propagate storage errors with `%w` so backend transaction runners can detect and retry transient contention errors (such as `status.Aborted`).

## 3. Keep Database-Specific Logic in Dedicated Subpackages
- The root `internal/storage` package ([`storage.go`](storage.go), [`test_utils.go`](test_utils.go)) must remain 100% database-agnostic. Never import database drivers or engine-specific types into `internal/storage`.
- Service and command layers (`cmd/`, `internal/`) must depend on `internal/storage` (`storage.Storage` or its domain sub-interfaces) rather than importing `internal/storage/spanner/<domain>` or `internal/storage/postgres/<domain>` directly.
- Every new domain repository must be wired into `storage.Storage` ([`storage.go`](storage.go)), [`internal/storage/spanner/spanner.go`](spanner/spanner.go), [`internal/storage/postgres/storage.go`](postgres/storage.go) (returning `codes.Unimplemented` in PostgreSQL if not yet implemented), and `storage.MockStorage` ([`test_utils.go`](test_utils.go)).
- Isolate all database-specific SQL dialects, mutations, schema mappings, and transaction mechanics inside dedicated engine subpackages:
  - [`internal/storage/spanner/`](spanner/) for Cloud Spanner
  - [`internal/storage/postgres/`](postgres/) for PostgreSQL
- Keep Spanner and PostgreSQL schemas and migrations in lockstep (enforced by [`parity_test.go`](migrations/parity_test.go); see [`README.md`](README.md#schemas-and-migrations) for the dual-backend workflow and no-op twin convention).

## 4. Deterministic Default Ordering & Pagination for Unbounded Collections
- **Explicit Newest-First Default Ordering (No Default Primary-Key ASC for Feeds)**: `TableView` and query generators for user-created, time-series, or unbounded entities MUST define an explicit default ordering via `OrderByFieldsWithSortDirection` (typically `created DESC` with a unique primary-key tie-breaker such as `id ASC`; hierarchical execution children scoped to a single parent such as `work_units` may order by sequence ID `ASC`). Never omit default ordering or fall back to primary-key or lexicographical `ASC` ordering on unbounded feeds, which truncates newly created entities from the first page once shared environments accumulate >100 historical records.
- **Server-Side Filtering & Pagination**: Always implement server-side filtering (`AIP-160`) and page-token pagination on `List*` queries instead of expecting callers to consume single-page results.
- **Multi-Page Pagination Test Coverage**: Unit and integration test suites for `List*` repositories MUST test pagination traversal across multiple pages (`N > page_size`) and verify that default sorting (empty `orderBy`) returns the view's declared default order (newest-first for feeds) consistently across page boundaries.

## 5. PostgreSQL Row Locking in Transactions
`pgdb.RunInTx` ([`postgres/pgdb/`](postgres/pgdb/)) runs `postgres.Storage.RunInTransaction` callbacks—and any repository-owned read-write transactions (such as [`postgres/operation/`](postgres/operation/))—at PostgreSQL's default `READ COMMITTED` isolation and retries `40001`/`40P01` up to `pgdb.DefaultMaxTxAttempts` times. A plain `SELECT` takes no row lock at this level, so concurrent read-modify-write transactions silently overwrite each other unless the read locks its rows. [`postgres/pausestate/`](postgres/pausestate/) and [`postgres/operation/`](postgres/operation/) are the reference implementations.
- **Make `pgdb.RunInTx` callbacks safe to re-run**: Because `pgdb.RunInTx` retries the callback on serialization failures (`40001`) and deadlocks (`40P01`), reset any outer state modified by the callback at the start of each attempt and keep side effects (such as logging diffs or external calls) outside the callback until `pgdb.RunInTx` succeeds.
- **Lock read-modify-write reads with `FOR NO KEY UPDATE`**: Any `*TxRepository` read whose result the same transaction writes back (such as `FetchExperiment`, `FetchWorkUnit`, `FetchUpdatingWorkUnits`, `FetchXidEntry`, and `PauseStateTxRepository.Get`) must end with `FOR NO KEY UPDATE`. Never use `FOR UPDATE`: it conflicts with the `FOR KEY SHARE` lock that foreign-key checks take on a parent row when child rows are inserted, which deadlocks concurrent writers.
- **Lock batches in primary-key order**: Multi-row locking reads must `ORDER BY` the primary key so concurrent transactions acquire row locks in the same order.
- **Lock the parent before allocating child IDs**: Aggregates such as `MAX(...)` cannot be locked. Run `SELECT 1 FROM <Parent> WHERE <Key> = $1 FOR NO KEY UPDATE` as a separate statement before computing the next child ID (such as `FetchNextWorkUnitID`) and before inserting a child row with a caller-supplied ID into the same parent (such as `InsertWorkUnit`).
- **Seed singleton rows before locking them**: Locking a missing row locks nothing. For singleton tables, `INSERT ... ON CONFLICT DO NOTHING` the default row first, then lock it with `SELECT ... FOR NO KEY UPDATE`.
- **Keep multi-statement reads consistent**: Non-transactional reads that span several statements must use a single SQL statement or a `REPEATABLE READ READ ONLY` transaction.
- **Prove each lock with a concurrency test**: Every read-modify-write path needs a [`postgrestest`](postgres/testing/)-backed test that runs concurrent `RunInTransaction` callbacks against the same row and asserts that no update is lost.

## 6. PostgreSQL Row Mapping, Named Arguments & `postgres/data/`
- **Treat ticket implementation recipes as hints, not mandates**: Storage ticket descriptions may suggest copying [`postgres/pausestate/`](postgres/pausestate/) or restricting edits to a single package. [`postgres/pausestate/`](postgres/pausestate/) is a 3-column scalar singleton; never extrapolate its inline positional `row.Scan` or `$1..$N` write lists to multi-column or protobuf-bearing repositories. Always follow the `postgres/data/` and `pgx` patterns below (exemplified by [`postgres/data/operation.go`](postgres/data/operation.go) and [`postgres/operation/`](postgres/operation/)).
- **Match `Repository` fields to transaction topology**:
  - **Standalone transactional repositories** ([`postgres/operation/`](postgres/operation/), `artifact`, `dashboard`) that run `pgdb.RunInTx` internally and do not participate in `storage.Transaction` hold `pool *pgxpool.Pool` only.
  - **Single-statement repositories** ([`postgres/pausestate/`](postgres/pausestate/), `pausedtask`, `statusmessage`, `statushistory`, `xid`, `clilogincode`) hold `db pgdb.DBTX` (and implement `WithTx(tx)` when part of `storage.Transaction`).
  - **Dual-mode repositories** (`experiment`, `workunit`) that implement `WithTx(tx)` for `storage.Transaction` *and* expose standalone read-modify-write methods (`UpdateExperiment`, `UpdateWorkUnit`) hold both `pool *pgxpool.Pool` (for `pgdb.RunInTx`) and `db pgdb.DBTX` (for `WithTx` and single-statement queries).
- **Isolate row structs and proto converters in [`postgres/data/`](postgres/data/)**: For tables with protobuf (`BYTEA` / `BYTEA[]`) columns or more than a few scalar columns, define **one** typed row struct (`*Row` with lowercase `db:"..."` tags matching PostgreSQL's folded column names) per table and pure `RowToProto` / `ProtoToRow` converters in [`internal/storage/postgres/data/`](postgres/data/), mirroring [`internal/storage/spanner/data/`](spanner/data/) (see [`postgres/data/operation.go`](postgres/data/operation.go) and [`postgres/operation/`](postgres/operation/)). Include write-only proto-derived columns (such as `Experiments.ActiveState`/`LaunchState`, `WorkUnits.QueueName`/`ExecutionState`/`ExecutionStatusMessageSeverity`/`PositionInQueue`, `Artifacts.PayloadType`/`SearchableContent`, and `Xids.Endpoint`) on that same `*Row` struct and populate them in `ProtoToRow`. Only trivial scalar-only singleton tables like [`postgres/pausestate/`](postgres/pausestate/) may scan inline.
- **Scan rows with `pgdb.QueryRow` / `pgx.CollectRows` + `pgx.RowToStructByNameLax`**: Execute single-row `SELECT` and `FOR NO KEY UPDATE` queries via `pgdb.QueryRow[T]` ([`postgres/pgdb/dbtx.go`](postgres/pgdb/dbtx.go)) and multi-row queries via `pgx.CollectRows(rows, pgx.RowToStructByNameLax[T])` instead of multi-variable positional `row.Scan(&col1, &col2, ...)`. Because `RowToStructByNameLax` leaves unselected struct fields at their zero values, partial `SELECT` column lists (such as `TableView` `*SelectFields` with `Selectable: false` columns omitted, `FetchedXIDColumns`, or `CurrentWorkUnitExecutionColumns`) scan directly into the table's single `*Row` struct. Always list `SELECT` columns explicitly—never use `SELECT *`, because `RowToStructByNameLax` fails if the SQL query returns a column not present on struct `T`. When implementing `List*` queries with `query_generator`, pass `querytools.DeduplicateSelects(true)`, omit `"bit_reversed_xid"` from PostgreSQL cursor maps, and type `WorkUnit` cursor `"state"` values as `int64` (matching `workunitschema.go`).
- **Bind multi-column writes with `pgx.StrictNamedArgs`**: In static `safesql.New` `INSERT` and `UPDATE` statements with multiple columns, use `@colname` placeholders paired with `pgx.StrictNamedArgs` (for example via `GetInsertArgs()` / `GetUpdateArgs()` methods on the `postgres/data/` row struct, as in [`postgres/data/operation.go`](postgres/data/operation.go)) to prevent positional `$1..$N` parameter drift or adjacent-column transposition. Keep positional `$1..$N` for simple primary-key `WHERE` lookups and `query_generator` filter predicates. Never build dynamic `INSERT`/`UPDATE` SQL strings from Go maps (randomized map iteration order thrashes the `pgx` prepared statement cache).
- **Use [`postgres/data/`](postgres/data/) helpers (`MarshalProto`, `MarshalNullableProto`) for `BYTEA` / `BYTEA[]` columns and preserve `NULL` vs `NOT NULL` semantics**: All PostgreSQL `BYTEA` columns share a single type OID (`17`), so driver-level `pgtype.Map` codecs cannot distinguish different protobuf message types. Marshal and unmarshal protobuf fields explicitly via shared helpers in [`postgres/data/`](postgres/data/) (`postgresdata.MarshalProto` for `NOT NULL` columns and `postgresdata.MarshalNullableProto` for nullable `BYTEA` columns so unset optional fields bind SQL `NULL` rather than `'\x'`) and unit-test them offline without Docker. On the read side, check `b != nil` (rather than `len(b) > 0`) for nullable `BYTEA` columns so valid empty protobuf messages (`'\x'`) are not dropped. For **`NOT NULL`** `BYTEA[]` and `TEXT[]` columns, initialize empty slices to non-nil (`[][]byte{}`, `[]string{}`) so `pgx` binds `'{}'` rather than SQL `NULL`. For foreign-key parent rows in integration tests, use `postgrestest.SeedExperiment` and `postgrestest.SeedWorkUnit` ([`postgres/testing/testdb.go`](postgres/testing/testdb.go)).
