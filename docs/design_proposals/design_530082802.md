Here are the clear answers to the design questions raised in the proposal, followed by the updated implementation plan.

### Answers to Design Questions

1. **Guarded Opt-In Policy for `Privileged: true` and `RunAsUser: 0`**:
   - **Resolution**: We will **not** implement a custom gate (e.g. tag checks, user lists) inside the XMC application code or validator for `privileged: true` or `run_as_user: 0`. Since XMC maps Kueue queues (`SchedulingConstraints.QueueName`) directly to Kubernetes namespaces, security boundaries are naturally enforced by the target Kubernetes cluster's Pod Security Admission (PSA) controller. If a user attempts to run a privileged workload on a queue/namespace restricted by Kubernetes policy (e.g. a `baseline` or `restricted` namespace), the Kubernetes API server will reject the `JobSet` creation. Delegating authorization to Kubernetes is standard practice and avoids duplicate access management logic in XMC.

2. **Capability Drops & Seccomp Profiles under Privileged Mode**:
   - **Resolution**: If a user explicitly sets `privileged = true` in the container's `SecurityContext`, XMC's actuator will **automatically** omit the default `Capabilities: {Drop: ["ALL"]}` list and force `AllowPrivilegeEscalation = true`. Standard hardware accelerator integrations (like TPU device access via `/dev/vfio`) require root privileges and capabilities that dropping `ALL` would block. Doing this automatically keeps the XMC API simple and avoids exposing complex Kubernetes-native capability configuration structures to XMC users.

3. **Code Comment Gaps & Violations**:
   - **Resolution**: The codebase comments in `defaultSecurityContext()` and `defaultPodSecurityContext()` warn against modifying the non-root/unprivileged defaults. Our design respects this warning. We will **not** modify `defaultSecurityContext()` or `defaultPodSecurityContext()`. Instead, we will construct new security contexts by merging the user-provided overrides on top of the hardcoded defaults. Jobs that do not specify a security context will continue to receive the secure defaults.

### Updated Technical Design & Implementation Plan: Workload Security Context & UID Overrides (Task 530082802)

#### 1. Executive Summary & Problem Analysis
XMC hardcodes pod and container security contexts inside `cmd/actuator/k8s_client/jobset.go`:
- Pods default to `RunAsUser: 1000`, `RunAsGroup: 1000`.
- Containers default to `Privileged: false`, `AllowPrivilegeEscalation: false`, and drop all capabilities.

ML workloads built expecting to run as `root` (UID `0`) or requiring hardware accelerator access (e.g., JAX/MaxText using `/dev/vfio`) fail immediately due to these restrictions. We will extend the API to allow users to override pod-level and container-level security contexts, validate these configurations, and apply the merged parameters in the actuator.

#### 2. Proposed Proto API Changes
Add `PodSecurityContext` (for pod-level overrides) and `SecurityContext` (for container-level overrides) messages in `api/protos/experiment/work_unit.proto`.

```protobuf
// In api/protos/experiment/work_unit.proto

// Pod-level security attributes applied across all containers in a KubernetesJob.
message PodSecurityContext {
  // The UID to run the entrypoint of the container process.
  // Defaults to 1000 if unset.
  optional int64 run_as_user = 1;

  // The GID to run the entrypoint of the container process.
  // Defaults to 1000 if unset.
  optional int64 run_as_group = 2;

  // Indicates that the container must run as a non-root user.
  // If true, the Kubelet validates the image at runtime to ensure it does not run as UID 0.
  optional bool run_as_non_root = 3;

  // A special supplemental group that applies to all containers in a pod for filesystem access.
  optional int64 fs_group = 4;
}

// Container-level security attributes applied to an individual ExecutableSpec.
message SecurityContext {
  // Run container in privileged mode. Processes inside a privileged container have
  // almost the same privileges as processes on the host (e.g., for /dev/vfio hardware access).
  optional bool privileged = 1;

  // Controls whether a process can gain more privileges than its parent process.
  optional bool allow_privilege_escalation = 2;

  // Container-specific UID override. Overrides PodSecurityContext.run_as_user if set.
  optional int64 run_as_user = 3;

  // Container-specific GID override. Overrides PodSecurityContext.run_as_group if set.
  optional int64 run_as_group = 4;

  // Container-specific non-root override. Overrides PodSecurityContext.run_as_non_root if set.
  optional bool run_as_non_root = 5;
}

message KubernetesJob {
  ...
  // Pod-level security context.
  optional PodSecurityContext security_context = 12;
}

message ExecutableSpec {
  ...
  // Container-level security context.
  optional SecurityContext security_context = 9;
}
```

#### 3. Validation Logic Changes
In `internal/validator/requests.go`:
- Validate that `run_as_user`, `run_as_group`, and `fs_group` are non-negative.
- Check for logical conflicts: reject configurations where `run_as_non_root` is effectively `true` but `run_as_user` resolves to `0` (either directly at the container level, or inherited from the pod level).

We will add validation tests in `internal/validator/requests_test.go` covering these validation rules and error scenarios.

```go
func buildPodSecurityContext(userSc *esspb.PodSecurityContext) *corev1.PodSecurityContext {
	sc := &corev1.PodSecurityContext{
		RunAsGroup: proto.Int64(1000),
		RunAsUser:  proto.Int64(1000),
		SeccompProfile: &corev1.SeccompProfile{
			Type: corev1.SeccompProfileTypeRuntimeDefault,
		},
	}
	if userSc == nil {
		return sc
	}
	if userSc.RunAsUser != nil {
		sc.RunAsUser = userSc.RunAsUser
	}
	if userSc.RunAsGroup != nil {
		sc.RunAsGroup = userSc.RunAsGroup
	}
	if userSc.RunAsNonRoot != nil {
		sc.RunAsNonRoot = userSc.RunAsNonRoot
	}
	if userSc.FsGroup != nil {
		sc.FSGroup = userSc.FsGroup
	}
	return sc
}

func buildContainerSecurityContext(userSc *esspb.SecurityContext) *corev1.SecurityContext {
	sc := &corev1.SecurityContext{
		AllowPrivilegeEscalation: proto.Bool(false),
		Capabilities: &corev1.Capabilities{
			Drop: []corev1.Capability{
				"ALL",
			},
		},
		Privileged: proto.Bool(false),
	}
	if userSc == nil {
		return sc
	}
	if userSc.Privileged != nil {
		sc.Privileged = userSc.Privileged
		if *userSc.Privileged {
			// A privileged container needs all capabilities and privilege escalation enabled.
			sc.Capabilities = nil
			sc.AllowPrivilegeEscalation = proto.Bool(true)
		}
	}
	if userSc.AllowPrivilegeEscalation != nil {
		sc.AllowPrivilegeEscalation = userSc.AllowPrivilegeEscalation
	}
	if userSc.RunAsUser != nil {
		sc.RunAsUser = userSc.RunAsUser
	}
	if userSc.RunAsGroup != nil {
		sc.RunAsGroup = userSc.RunAsGroup
	}
	if userSc.RunAsNonRoot != nil {
		sc.RunAsNonRoot = userSc.RunAsNonRoot
	}
	return sc
}
```
